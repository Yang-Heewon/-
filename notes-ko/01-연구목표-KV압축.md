# 연구 목표 — VLM/GUI 에이전트를 위한 KV 캐시 압축

*(2026-08-13 기준 정리)*

## 한 줄 요약

**"질문(query)을 모르는 상태에서도 유효한" KV 캐시 압축 방법**을 만드는 것이 목표입니다.
점수는 두 축으로 매깁니다:

1. **인코더 saliency (공간 축)** — 비전 인코더가 이미지의 어느 부분을 중요하게 보는가
2. **프레임 간 시간적 중복 (시간 축)** — 연속 스크린샷에서 반복되는 영역은 중복이므로 버릴 수 있다

동기(motivation)는 이렇습니다: 기존의 query-aware 압축 방법들(SnapKV, H2O, PyramidKV, FastV)은
**"지금 들어온 질문"에 맞춰 캐시를 압축**하기 때문에, 그 캐시를 **아직 알 수 없는 미래의 다른 지시(instruction)에 재사용하면 무너진다**는 것을 실험으로 보여주는 것입니다.

## 이 연구가 성립하는지 판가름하는 관문 실험 2개 (가장 먼저 실행할 것)

1. **P2 (D1)**: 기존 압축 방법이 **같은 예산(budget)에서 텍스트 전용 태스크는 정확도를 유지하지만, GUI/문서 태스크에서는 실패**해야 합니다.
   → 만약 GUI 태스크가 20% 예산에서도 멀쩡하다면, **애초에 쓸 문제가 없는 것**입니다.

2. **D3 oracle sanity check**: KV를 마스킹했을 때 **정답(gold answer)의 logprob가 실제로 떨어지는지** 확인해야 합니다.
   → 마스크가 조용히 무시되고 있다면 D3, D4 실험 모두 의미가 없어집니다.

## 꼭 기억할 설계 교정 사항

**중요도(importance)는 반드시 oracle 방식으로 측정해야 합니다** — 즉, 토큰 그룹을 하나씩 빼보고(leave-group-out KV ablation) 정답 logprob가 얼마나 변하는지(Δ logprob)로 측정합니다.

**norm끼리의 상관관계로 측정하면 안 되는 이유**: V(value)는 hidden state의 선형 사영(linear projection)이기 때문에, "인코더 norm ↔ value norm" 상관은 **구조상 당연히 나오는 결과**이지 증거가 아닙니다.

또한 항상 **패치 픽셀 분산(patch pixel variance)이라는 공짜 대조군**을 넣어야 합니다. 만약 인코더 saliency가 픽셀 분산과 똑같은 성능이라면, "인코더 신호가 기여한다"는 주장은 무너집니다.

## 프레이밍 업데이트 (2026-08-13)

프로젝트의 상위 목표를 **"압축된 시각 KV = 에이전트의 장기 기억(long-term memory)"**으로 확장했습니다. 단순한 서빙 효율(serving efficiency) 이야기가 아닙니다. 이로 인해 요구사항이 3개 추가됩니다 (`PRIOR_WORK.md` §5 참조):

- **R1 — query-agnostic 유효성** (D4 실험): 압축된 KV가 어떤 미래 질문에도 쓸 수 있어야 함
- **R2 — 저장된 KV의 위치 이식성** (신규 D6a 실험): 다른 컨텍스트 위치에 KV를 옮겨 넣어도 작동해야 함.
  - **mRoPE 가설**: 시간(temporal) 축만 다시 회전(re-rotate)시키면 되고, 공간(spatial) 축은 위치가 일관되므로 그대로 둬도 된다.
  - 이것은 **관문(gate) 실험**입니다 — 실패하면 "장기 기억" 프레임은 버립니다.
- **R3 — 저장 비용 경제성**: 스크린샷 1,000장의 KV 뱅크는 비압축 시 **145–372 GB** → "비용" 스토리가 저장 용량 관점에서 되살아남.
  - D0 + D6b Pareto 비교: 이미지 저장 후 re-prefill vs 전체 KV vs 압축 KV vs 텍스트 요약

**Gap G5 확인 — 아직 열려 있음**: Mem-W (arXiv 2605.09317)는 *학습된* latent 토큰을 저장하는 것이지 KV가 아니고, PromptCache/CacheBlend/C²KV 같은 KV 지속성(persistence) 연구는 전부 텍스트 전용입니다.

## 신호 사용 범위 교정 (2026-08-13)

제약 조건은 **"인코더만 써야 한다 / 엄격한 query-agnostic"이 아닙니다.**
메모리에 기록하는 시점(write-time)에는 에피소드가 이미 끝나 있으므로, 그 시점에 존재하는
신호 — 실행된 지시문, **디코딩된 출력/행동**, 그때의 attention — 는 전부 압축에 써도 됩니다.
금지되는 정보는 딱 하나, **미래의 읽기 시점(read-time)에 올 질문**입니다.

따라서 연구 질문은 이렇게 재정의됩니다:
**"write-time에 쓸 수 있는 신호 중 어떤 것이 미래의 unknown 질문에 일반화되는가?"**
→ D4 전이 행렬이 정확히 이것을 측정 (대각 = 자기 질문 성능, 비대각 = 일반화).

D4에서 비교할 신호 후보:
1. 자기 질문의 attention (SnapKV 방식)
2. 디코딩된 출력까지 포함한 누적 attention (H2O 방식)
3. 인코더 saliency (이미지만 사용)
4. 픽셀 분산 (공짜 대조군)
5. 여러 질문의 union / 재구성 질의 (KVzip 방식 — KVzip은 텍스트 전용이라 VLM 확장은 열려 있음)

**R3의 정직한 프레이밍**: 스크린샷 PNG(~0.5–2 MB)는 그 KV(비압축 ~145 MB)보다 훨씬 작으므로,
압축 KV의 가치는 저장 용량이 아니라 **회상(recall) 시점의 연산 절약**(re-prefill FLOPs/TTFT
생략)입니다. 방법의 목표는 이 trade가 매력적일 만큼 저장 프리미엄을 줄이는 것.

## 시스템 차원의 최종 그림 (2026-08-13)

우산이 되는 목표는 **메모리 시스템**입니다: 쓸 때(write) 분류/정리해서 저장하고,
읽을 때(read) 필요한 것만 골라 가져오되, 가져온 메모리가 컨텍스트에서 **토큰을 적게
차지**하도록 하는 구성. 일단 VLM(스크린샷)으로 시작.

"토큰을 덜 쓴다"는 두 가지로 분리됩니다:

1. **어떤 메모리를 불러올지 고르기** = 검색/인덱싱. 텍스트 설명자나 임베딩을 키로 쓰는
   표준 부품으로 해결 — **여기는 novelty가 아님.**
2. **불러온 메모리가 컨텍스트에서 얼마를 차지하는가** = 압축 KV. **여기가 novelty**이고,
   D3/D4/D6a/D6b가 이 기판(substrate)을 검증하는 실험.

이렇게 보면 D6b의 4개 선택지는 경쟁자가 아니라 **한 계층 구조의 티어**가 됩니다:
인덱스(~KB) → 압축 KV(본체 payload) → 원본 이미지 re-prefill(fallback).

**추가 기술 리스크 (D6c 후보)**: 검색된 KV 블록 **여러 개**를 한 컨텍스트에 꽂으면
블록 간 attention이 계산된 적이 없다는 문제. CacheBlend가 텍스트에서 부분 재계산으로
해결했지만 VLM에서는 미해결 — 우리 갭에 포함됨.

**스쿱 상태**: 텍스트 메모리 시스템(MemGPT/Mem0/A-Mem)과 텍스트 청크 KV 재사용
(PromptCache/CacheBlend/TurboRAG/CAG)은 이미 존재. **"검색 단위 = 압축된 시각 KV 블록"은
여전히 아무도 안 함 (G5).**

엔드투엔드 메모리 뱅크 데모(토큰 비용 회계 포함)는 논문의 **마무리 데모(capstone)**이지
헤드라인이 아님 — 헤드라인은 여전히 D4.

## D0-cost — "저장이 연산보다 싸다"는 주장 자체를 검증 (2026-08-13)

이 주장은 가정이 아니라 검증 대상. 봉투 뒷면 계산으로도 결론이 자명하지 않음:

- 이미지 1장 기준: 비압축 KV 저장(~145 MB ≈ 월 $0.003, S3) ≈ **re-prefill 5–15회**
  (회당 ~$0.0002–0.0006, GPU ~1초). → 회상 빈도가 낮으면 달러로는 이미지+re-prefill이 이김.
- **압축률이 손익분기점을 직접 움직임**: 20% 압축이면 손익분기 ~월 1회 회상으로 내려옴.

보고할 양은 3개로 분리:

1. **달러**: 공개 클라우드 가격 기반 **손익분기 회상 빈도 곡선**
2. **지연시간(TTFT)**: KV 로드는 대역폭 바운드 (NVMe ~20–70ms/장) vs prefill은 연산 바운드
   (~1초) — 약 10배 차이. V100 박스에서 직접 측정 (cold/warm, 디스크→PCIe→GPU 전체 파이프라인).
   단 10스텝 trajectory(1.5–3.7 GB)면 로드도 0.5–1.8초로 올라와 격차가 줄어듦 → 압축률이 결정.
3. **처리량**: prefill 생략으로 확보되는 배치 동시성 (tokens/s)

산출물: D6b Pareto에 비용 축 추가 — "회상 빈도 X 이상이면 압축 KV가 지배" 그림.
비용 주장을 스스로 공격해 살아남는 구간을 명시하는 것은 B(통제된 반박) 스탠스와 일관됨.
